# 管理页摄像头分组与录音控制设计

## 状态

已确认设计，尚未实施。

## 目标

- 在现有 Tailscale 管理页增加“摄像头”区域，不改变公网客户页面的管理权限边界。
- 摄像头缩略图、分组状态、录音滑块和“应用并重启”只存在于管理页面；客户监控浏览页面不得出现这些管理内容。
- 页面打开时，每路摄像头只读取一次 Frigate 已有的低清 `latest.jpg`，不建立直播连接、不自动刷新。
- 所有画面默认横向排列；同组画面紧凑排列，不同组之间增加明显但克制的间距。
- 每组画面下方提供一个“录制声音”滑块，同时控制组内全部摄像头。
- 滑块只产生待应用状态；管理员统一点击“应用并重启”，一次提交全部更改并只重启一次 Frigate。
- 对含音轨的历史录像，在回放全屏时允许用户手动开启当前画面的声音；双画面状态继续默认静音。
- 管理页从首版开始预留第二组的两个摄像头位置；未接入时显示占位状态且不请求 Frigate 图片。

## 页面布局

“摄像头”区域放在设备统计卡片下方、观看设备列表上方。

```text
摄像头                                             [应用并重启]

院子
[云台低清图][固定低清图]      门前
  云台画面    固定画面          [待接入][待接入]
[录制声音 关闭]                 [录制声音 待接入]
```

布局规则：

- 桌面端所有摄像头组在同一横向流中排列。
- 组内使用较小间距，组间使用约两倍间距，并通过组名强化归属。
- 宽度不足时整组换行，不能把一个组的两个画面拆到不同行。
- 每组滑块位于该组全部缩略图下方，而不是放在单路画面内部。
- “应用并重启”固定在摄像头区域标题右侧；没有待应用更改时禁用。
- 第二组始终保留两个固定画面位。摄像头未配置时显示“待接入”，配置完成后在原位置替换为低清图，不重新设计页面结构。
- 一组尚未接入任何摄像头时，该组录音滑块禁用并显示“待接入”；至少接入一路后才允许产生待应用设置。

## 数据模型

Portal 增加显式摄像头组配置。组是录音控制和页面布局的最小单位；摄像头仍保留各自的 Frigate ID 与显示名称。

```text
CameraGroup
  id
  name
  cameras[]

Camera
  id（尚未接入时可为空）
  name
  slot
```

同一组内所有摄像头必须使用相同的录像音频设置。如果读取到组内状态不一致，管理页显示“配置不一致”，滑块进入不确定状态；管理员选择目标状态并应用后统一修正。

每组固定定义两个 `slot`。只有配置了有效 Frigate 摄像头 ID 的 slot 才参与图片读取和录音设置；占位 slot 只负责保留布局。

## 读取流程

1. 管理页首次加载摄像头组与 Frigate 当前有效配置。
2. Portal 通过 Docker 私网访问 Frigate 内部 API，判断每路录像输出是无声预设还是 AAC 音频预设。
3. 浏览器只为已接入的摄像头请求一张高度约 180px、质量约 60 的低清图；预留位置不发请求。
4. 图片响应设置 `Cache-Control: no-store`，且只允许从 Tailscale 管理入口读取。
5. 现有每 30 秒一次的观看设备刷新不能重新加载摄像头图片；如需更新，另设显式“刷新画面”按钮。

实测当前低清图片约 14–15KB/路、生成约 8ms。四路首次加载约 60KB，对服务器和网络影响可忽略。

## 应用录音设置

滑块只修改浏览器中的待应用值，不立即操作 Frigate。

点击“应用并重启”后：

1. 弹窗明确提示：所有直播和录像可能中断 15–60 秒；仅影响新录像，历史录像不变。
2. 前端提交所有发生变化的摄像头组，随后锁定滑块和应用按钮。
3. Portal 串行处理本次操作，拒绝并发应用请求。
4. Portal 读取并保留旧值，然后通过 Frigate 内部配置 API 批量设置组内所有摄像头：
   - 无声：`preset-record-generic`
   - 有声：`preset-record-generic-audio-aac`
5. Frigate 完成配置校验后，Portal 只触发一次整体重启。
6. Portal 轮询 Frigate 健康状态；恢复后重新读取有效配置并更新滑块。
7. 配置写入失败时不重启并恢复界面；重启后未恢复时显示明确错误和“重试”入口，不伪装成功。

不实现单路热切换，也不通过 Docker Socket 控制容器。Frigate 0.17.2 的录像 FFmpeg 输出参数不支持热更新，整体重启是受支持且可维护的路径。

## 回放声音

本节是客户监控浏览页面的独立播放能力，仅用于让有音轨的录像可以被听到；它不承载摄像头管理、分组设置或录音开关。

- 双画面回放继续默认静音，以满足浏览器自动播放规则并避免声音叠加。
- 进入单画面全屏后，用户可通过小喇叭按钮开启当前录像声音。
- 同一时间最多一条录像输出声音；退出全屏、切换日期、切换摄像头或离开回放模式时立即静音。
- 没有音轨的录像仍可正常播放，小喇叭显示不可用或保持静音。
- 本期不实现直播声音。

## 安全与可靠性

- 新的摄像头状态、快照和录音修改接口仅注册在现有 AdminHandler，继续受 Tailscale 用户白名单保护。
- 客户监控浏览页面只保留直播与回放，不渲染管理页摄像头卡片、占位卡片、录音状态或应用按钮。
- 写操作继续校验同源 `Origin`、管理请求头和允许的摄像头/组 ID。
- 公网 PublicHandler 不注册任何管理路由；测试必须确认对应 URL 返回 404。
- Portal 只调用已有 Frigate Docker 私网 API，不挂载配置目录，不挂载 Docker Socket。
- 服务端只接受两个固定录像预设，不能由浏览器提交任意 FFmpeg 参数。
- 应用过程写结构化日志，但不得记录摄像头密码、原始 RTSP URL 或完整 Frigate 配置。

## 测试与验收

- 桌面宽屏：所有组横排；组内间距小于组间间距。
- 窄屏：按整组换行，组内画面不被拆散。
- 首次打开每路图片只请求一次；30 秒设备刷新不触发图片请求。
- 未修改滑块时“应用并重启”不可用。
- 多组同时修改只产生一次 Frigate 重启。
- 配置无效、Frigate API 失败和重启超时均有可理解的错误状态。
- 公网入口无法访问摄像头管理、快照或录音修改接口。
- 关闭录音后新分片无音轨；开启后新分片含 AAC 音轨；历史文件不变化。
- 双画面无声；全屏只允许当前录像发声；退出全屏后恢复静音。

## ADR：采用组级待应用设置和单次重启

### 决策

采用“组级滑块 → 待应用状态 → 应用并重启”的方式，不采用滑块即刻生效或单路 FFmpeg 热切换。

### 正面影响

- 摄像头组与物理设备保持一致，避免双镜头设置漂移。
- 多组变更只重启一次，减少录像缺口和误操作。
- 不修改 Frigate 源码，后续升级维护成本低。
- 不扩大 Portal 权限到 Docker Socket。

### 负面影响

- 应用设置时全部摄像头短暂中断。
- 开关不是即时生效，需要额外点击一次应用按钮。

### 未采用方案

- 每个滑块立即重启：容易连续重启并扩大录像缺口。
- 每路独立滑块：灵活性有限，却容易让同一物理设备配置不一致。
- 自定义 Frigate 热切换：开发和升级风险明显高于本项目收益。
